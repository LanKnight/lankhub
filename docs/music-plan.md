# 清弦（`/music`）在线播放功能 · 方案与实测记录

> 本文档记录**实测**结论，不是照抄 `musicFunctionDevDoc.md`。
> 实测中发现了若干与那份文档不一致的地方，凡是影响设计的都记在下面。

## 一、API 实测结论

基础地址 `https://music-api.gdstudio.xyz/api.php`，无需登录、无需 Key。
实测时间：2026-10，由 `scripts/_probe-music-api*.py` 逐个验证（脚本已删除）。

| 验证项 | 结果 |
| --- | --- |
| `types=search`（netease） | HTTP 200，字段与文档一致 |
| `types=url`（netease，br=320） | HTTP 200，返回真实 `.mp3` 签名地址 |
| `types=pic`（netease） | HTTP 200 |
| `types=lyric`（netease） | HTTP 200，标准 LRC |
| **`kuwo`** | **HTTP 400 `Value of source is not supported`** |
| **`joox`** | 搜索 200，但 `types=url` 恒返回空链接（`= 编码`与`原样`两种写法都试过） |
| 其余 11 个音源 | 全部 HTTP 400 不支持（tencent / kugou / migu / tidal / qobuz / spotify / apple / ytmusic…） |

### 由此得到的四条硬结论

1. **`netease` 是唯一真正能播的音源。**
   文档推荐的备用链 `netease → kuwo → joox` 是**双层失效**的：
   kuwo 被服务端直接拒绝，joox 能搜不能放。
   查了根源：**API 自己的 `api.php` 文档页仍然列着 kuwo**，
   所以不是那份文档抄错，而是 **API 的实现与它自己的文档不一致**。
   → 代码里**不做多音源轮询**，失败就重试 netease，不要浪费请求去试已知不可用的音源。

2. **播放地址是短时签名，但支持 Range。**
   URL 形如 `.../20261007144126/....mp3`，**两次请求得到的 URL 不同**，
   说明带时间戳签名、有有效期。
   同时实测响应头为：
   - `Content-Type: audio/mpeg`
   - `Accept-Ranges: bytes`
   - `Access-Control-Allow-Origin: *`
   - 带 `Range: bytes=0-1023` 的请求返回 **HTTP 206**
   → **进度条拖动可用**；**播放地址不能长期缓存**。

3. **CORS 只需解决 JSON 接口。**
   `<audio src>` 与 `<img>` 不受同源策略约束，直连 CDN 即可；
   但 `fetch` 那个 JSON 接口会被 CORS 拦下 → **必须走后端代理**。

4. **限流 60 次 / 5 分钟 → 缓存是必需项，不是优化项。**
   一个访客点 10 首歌 = 30 次调用（url + pic + lyric），两个访客就能吃光配额。
   → 采用下面 3.2 的两层缓存。

### 补充实测（2026-10，做后台绑定界面时又确认的几条）

5. **`types=search` 的返回里没有封面地址。**
   完整字段只有 9 个：
   `id / name / artist / album / pic_id / url_id / lyric_id / source / from`。
   而封面的 CDN 地址形如
   `https://p2.music.126.net/<加密哈希>/<pic_id>.jpg?param=300y300`，
   那段哈希**无法由 pic_id 推导** —— 实测
   `p2.music.126.net/{picId}.jpg` 与 `p2.music.126.net/{picId}/{picId}.jpg`
   **都是 404**，只有接口给的那种带哈希的地址返回 **206 / image/jpg**。
   → **搜索结果里想显示封面，就只能为每条候选调一次 `types=pic`**，
     一次搜索十几条候选会瞬间吃光配额。所以后台的候选列表
     **刻意不显示封面**，挑原版靠歌手与专辑（这两项本来就够分辨翻唱）。
     已绑定入库的歌则直接用存下来的 `coverUrl`，零调用。

6. **搜索关键词用「歌名 + 歌手」召回更好。**
   实测 7 首歌对比两种写法：
   「起风了 冯沁苑」拿到 **9 条歌名精确相同**的候选，只搜歌名只有 5 条；
   「演员 薛之谦」两种写法原版都在，但带上歌手后同名候选更集中。
   → `/match` 与 `prisma/bind-music.ts` 都改用「歌名 + 歌手」。

7. **接口的相关度排序对「原版」并不友好，必须本地重排。**
   实测「大鱼 - 周深」的可信原版排在候选**第 8 位**，前面 7 条全是翻唱。
   所以 `matchSong` 不再取「第一条歌名相同的」，而是在候选里
   **自己找第一条歌名精确 + 歌手可信的**；找不到可信的但歌名对得上时
   返回 `confidence: "low"` 与 `titleMatches`，交给人判断 —— 代码不替用户拍板。
   （候选回传条数也因此从 8 提到 10：第 8 位那一条差点被截断漏掉。）

8. **网易云无版权的歌，两种搜索写法都救不回来。**
   「晴天 / 稻香 / 青花瓷 / 兰亭序 + 周杰伦」实测两种策略下
   **可信候选都是 0 条**，搜出来全是冒用「周杰伦.」「Jay」这类名字的翻唱。
   `matchSong` 返回 null 是**正确结果**，不是失败 —— 这些歌走外链。

## 二、方案

### 2.1 数据模型（`Song` 扩展，全部可空，纯追加、不动现有数据）

| 字段 | 用途 |
| --- | --- |
| `source` | 音源，默认 `"netease"` |
| `apiId` | 播放用的 `url_id`；**为空 = 尚未绑定** |
| `picId` / `lyricId` | 取封面与歌词用的 ID |
| `coverUrl` | 绑定时抓取入库的封面地址 |
| `lyric` | 绑定时抓取入库的 LRC 原文 |
| `album` | 专辑名 |

### 2.2 两层缓存

- **DB 缓存（永久）**：`coverUrl` 与 `lyric` 在**绑定那一刻**就抓下来存库。
  → 前台渲染卡片墙与歌词是**零 API 调用**。
- **内存缓存（短）**：播放地址是签名短时的，只缓存 **5 分钟**，失败自动重取。

前端只与自己的服务器通信（`connect-src 'self'` 不用改）。

### 2.3 运行时接口面（刻意做小）

- `GET /api/music/play?id={songId}` —— 唯一对访客开放的接口，带频率限制。
  带 `&retry=1` 时**跳过服务端的内存缓存**重新取地址：播放器播到一半
  发现地址失效（用户暂停很久再继续）时会带这个参数回来重试，
  并从断掉的进度续播。没有这个参数的话重试只会拿回同一条坏地址。
- 前台**不做搜索**：既符合「我喜欢的音乐」的定位，也不会让公开访客
  无限消耗 60 次/5 分钟的配额，版权暴露面也最小。

后台侧（站长专属）：搜索、单条绑定 / 解绑、批量自动匹配（带确认预览）。

### 2.4 CSP

音频与封面直连 CDN，因此需要放宽两个指令：

```
media-src 'self' https://*.music.126.net
img-src   'self' data: blob: https://*.music.126.net
```

一个通配符同时覆盖音频（`m701/m801.music.126.net`）与封面（`p1/p2.music.126.net`）。
`connect-src` 保持 `'self'` 不变。选择这条而不是由服务器代理音频，
是为了不让 ECS 承担全部音频流量（320kbps ≈ 2.4MB/分钟/人）。
若将来发现 CDN 更换域名导致播放失败，再改为服务器代理。

## 三、来源标注与免责

- 播放器旁一行小字：数据来源 GD音乐台 · 仅供个人学习
- 独立页 `/music/disclaimer`：完整免责声明
- 页脚加链接
- **侵权联系方式取自简历页（`ResumeProfile`）的邮箱与电话**，
  不另外硬编码一份联系方式，避免出现第二个真相源
- 不提供任何下载入口

## 四、界面

- **卡片墙**：按歌手分组的网格卡片，显示歌手、歌曲数、该歌手推荐曲的封面
  （封面取自已入库的 `coverUrl`，零调用）；点击卡片**就地展开**露出歌单
- **底部固定播放条**：封面 + 歌名歌手 + 播放/暂停 + 上下一首 +
  可拖动进度条 + 音量；移动端压缩为紧凑版
- **歌词抽屉**：LRC 解析 + 滚动高亮
- **后台歌单管理**（`/admin/music`）：
  - 每行显示封面缩略图 + 绑定状态徽标（已绑定 / 源站无原版 / 待绑定），
    未绑定的给「搜索绑定」、已绑定的给「解绑」
  - 工具栏：配额剩余、`[自动匹配未绑定的歌]`、`[清除全部绑定]`（二次确认）
  - 批量自动匹配是**两段式**：先分批调 `/match` 只搜不写，结果逐条列出
    让人确认（高置信度直接可绑；歌名相同但歌手对不上的一律提示「只有翻唱」），
    再调 `/bind` 写入，没匹配上的放进 `markNoMatch`

## 五、后台绑定界面的验证记录（2026-10）

真跑了一遍：临时改站长密码 → 真实登录 → 造 3 首歌 → 匹配 → 绑定 →
查库核对 → 前台取播放地址 → 解绑 → 清理，**29 项断言全过**；
另加 21 项渲染层断言与 17 项 `matchSong` 单元断言。
关键的几条实测结果：

- 演员 - 薛之谦 → 匹配到「演员 — 薛之谦（绅士）」并成功写入
  `apiId=32507038`、封面、歌词 1276 字、专辑「绅士」
- 起风了 - 冯沁苑 → 认作合法别名，匹配到「冯沁苑(买辣椒也用券)」
- 晴天 - 周杰伦 → `confidence=low`、**不绑定**、标记 `nomatch`，
  且仍有候选供人工挑选（符合「只给外链、不绑翻唱」的决定）
- 单首歌的播放地址是按需现取的签名地址：两条不同的歌各拿到不同 URL
- 未绑定的歌 `/api/music/play` 返回 **409** 并带上外链，前端据此退到「去别处听」
- `matchSong` 在「原版被压在候选第 5 位」的构造样例里能正确挑出原版；
  「周杰伦.」「周杰伦♚」「周杰伦的歌」「HF薛之谦」「Jay」全部判为不可信

**验证时踩到的两个坑**（记下来免得重复）：

1. 断言封面时我用了自己拼的 `p2/{picId}.jpg`，且判定条件是
   「URL 字符串出现在页面里」→ 看着通过了，其实那个地址是 **404**。
   **断言必须用接口真实返回的地址，并且最好验证它真的能取到图。**
2. 前台卡片墙在 SSR 里**只有折叠状态的歌手卡片**，歌曲列表要点击才展开渲染，
   所以行内的「待绑定」徽标在首屏 HTML 里根本不存在。
   对这类内容的断言要改成查 flight 数据（如 `apiId`）或查前端产物，
   不能断言首屏 HTML 里有这段文字。

**这一轮验证真抓出来的三个功能缺陷**（都是先写断言、才发现的）：

1. **`SongBindSchema` 的 `items` 写死了 `.min(1)`** → 后台「标记无原版」
   这个只标记、不绑定的动作会被 **400 拒掉**，按钮点下去其实是坏的。
   改成 `items` 允许空数组 + `refine` 保证「两者不能都空」。
2. **`/match` 根本没排除 `matchStatus = "nomatch"` 的歌** →
   「标记后不再重复搜它」这句当时是**假的**，标记只影响计数显示。
   加过滤时又差点踩第二个坑：`{ not: "nomatch" }` 在 SQL 里
   `NULL <> 'nomatch'` 结果是 **NULL 而不是 true**，会把所有「没搜过」
   的新歌一起滤掉（自动匹配直接废掉）。必须写成显式 OR。
3. **`/unbind` 顺手把 `matchStatus` 也清了** →
   「清除全部绑定」一键就把当初判定无版权的结论抹掉，下次又白搜一遍。
   「有没有绑定」与「搜过有没有原版」是两件事，不该一起清。

**仍未在真实浏览器里听过声音**（见交接文档 7.6）：播放、拖动进度条、
歌词滚动、以及「地址失效后自动重取并续播」都是浏览器行为，需要人工点一遍。
