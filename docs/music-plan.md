# 清弦（`/music`）在线播放功能 · 方案与实测记录

> 本文档记录**实测**结论，不是照抄 `musicFunctionDevDoc.md`。
> 实测中发现了若干与那份文档不一致的地方，凡是影响设计的都记在下面。

## 一、API 实测结论

基础地址 `https://music-api.gdstudio.xyz/api.php`，无需登录、无需 Key。
实测时间：2026-10，由 `scripts/_probe-music-api*.py` 逐个验证（脚本已删除）。

| 验证项 | 结果 |
| --- | --- |
| `types=search`（netease） | HTTP 200，字段与文档一致 |
| `types=url`（netease，br=320） | HTTP 200，返回真实 `.mp3` 签名地址 |
| `types=pic`（netease） | HTTP 200 |
| `types=lyric`（netease） | HTTP 200，标准 LRC |
| **`kuwo`** | **HTTP 400 `Value of source is not supported`** |
| **`joox`** | 搜索 200，但 `types=url` 恒返回空链接（`= 编码`与`原样`两种写法都试过） |
| 其余 11 个音源 | 全部 HTTP 400 不支持（tencent / kugou / migu / tidal / qobuz / spotify / apple / ytmusic…） |

### 由此得到的四条硬结论

1. **`netease` 是唯一真正能播的音源。**
   文档推荐的备用链 `netease → kuwo → joox` 是**双层失效**的：
   kuwo 被服务端直接拒绝，joox 能搜不能放。
   查了根源：**API 自己的 `api.php` 文档页仍然列着 kuwo**，
   所以不是那份文档抄错，而是 **API 的实现与它自己的文档不一致**。
   → 代码里**不做多音源轮询**，失败就重试 netease，不要浪费请求去试已知不可用的音源。

2. **播放地址是短时签名，但支持 Range。**
   URL 形如 `.../20261007144126/....mp3`，**两次请求得到的 URL 不同**，
   说明带时间戳签名、有有效期。
   同时实测响应头为：
   - `Content-Type: audio/mpeg`
   - `Accept-Ranges: bytes`
   - `Access-Control-Allow-Origin: *`
   - 带 `Range: bytes=0-1023` 的请求返回 **HTTP 206**
   → **进度条拖动可用**；**播放地址不能长期缓存**。

3. **CORS 只需解决 JSON 接口。**
   `<audio src>` 与 `<img>` 不受同源策略约束，直连 CDN 即可；
   但 `fetch` 那个 JSON 接口会被 CORS 拦下 → **必须走后端代理**。

4. **限流 60 次 / 5 分钟 → 缓存是必需项，不是优化项。**
   一个访客点 10 首歌 = 30 次调用（url + pic + lyric），两个访客就能吃光配额。
   → 采用下面 3.2 的两层缓存。

### 补充实测（2026-10，做后台绑定界面时又确认的几条）

5. **`types=search` 的返回里没有封面地址。**
   完整字段只有 9 个：
   `id / name / artist / album / pic_id / url_id / lyric_id / source / from`。
   而封面的 CDN 地址形如
   `https://p2.music.126.net/<加密哈希>/<pic_id>.jpg?param=300y300`，
   那段哈希**无法由 pic_id 推导** —— 实测
   `p2.music.126.net/{picId}.jpg` 与 `p2.music.126.net/{picId}/{picId}.jpg`
   **都是 404**，只有接口给的那种带哈希的地址返回 **206 / image/jpg**。
   → **搜索结果里想显示封面，就只能为每条候选调一次 `types=pic`**，
     一次搜索十几条候选会瞬间吃光配额。所以后台的候选列表
     **刻意不显示封面**，挑原版靠歌手与专辑（这两项本来就够分辨翻唱）。
     已绑定入库的歌则直接用存下来的 `coverUrl`，零调用。

6. **搜索关键词用「歌名 + 歌手」召回更好。**
   实测 7 首歌对比两种写法：
   「起风了 冯沁苑」拿到 **9 条歌名精确相同**的候选，只搜歌名只有 5 条；
   「演员 薛之谦」两种写法原版都在，但带上歌手后同名候选更集中。
   → `/match` 与 `prisma/bind-music.ts` 都改用「歌名 + 歌手」。

7. **接口的相关度排序对「原版」并不友好，必须本地重排。**
   实测「大鱼 - 周深」的可信原版排在候选**第 8 位**，前面 7 条全是翻唱。
   所以 `matchSong` 不再取「第一条歌名相同的」，而是在候选里
   **自己找第一条歌名精确 + 歌手可信的**；找不到可信的但歌名对得上时
   返回 `confidence: "low"` 与 `titleMatches`，交给人判断 —— 代码不替用户拍板。
   （候选回传条数也因此从 8 提到 10：第 8 位那一条差点被截断漏掉。）

8. **网易云无版权的歌，两种搜索写法都救不回来。**
   「晴天 / 稻香 / 青花瓷 / 兰亭序 + 周杰伦」实测两种策略下
   **可信候选都是 0 条**，搜出来全是冒用「周杰伦.」「Jay」这类名字的翻唱。
   `matchSong` 返回 null 是**正确结果**，不是失败 —— 这些歌走外链。

## 二、方案

### 2.1 数据模型（`Song` 扩展，全部可空，纯追加、不动现有数据）

| 字段 | 用途 |
| --- | --- |
| `source` | 音源，默认 `"netease"` |
| `apiId` | 播放用的 `url_id`；**为空 = 尚未绑定** |
| `picId` / `lyricId` | 取封面与歌词用的 ID |
| `coverUrl` | 绑定时抓取入库的封面地址 |
| `lyric` | 绑定时抓取入库的 LRC 原文 |
| `album` | 专辑名 |

### 2.2 两层缓存

- **DB 缓存（永久）**：`coverUrl` 与 `lyric` 在**绑定那一刻**就抓下来存库。
  → 前台渲染卡片墙与歌词是**零 API 调用**。
- **内存缓存（短）**：播放地址是签名短时的，只缓存 **5 分钟**，失败自动重取。

前端只与自己的服务器通信（`connect-src 'self'` 不用改）。

### 2.3 运行时接口面（刻意做小）

- `GET /api/music/play?id={songId}` —— 唯一对访客开放的接口，带频率限制。
  带 `&retry=1` 时**跳过服务端的内存缓存**重新取地址：播放器播到一半
  发现地址失效（用户暂停很久再继续）时会带这个参数回来重试，
  并从断掉的进度续播。没有这个参数的话重试只会拿回同一条坏地址。
- 前台**不做搜索**：既符合「我喜欢的音乐」的定位，也不会让公开访客
  无限消耗 60 次/5 分钟的配额，版权暴露面也最小。

后台侧（站长专属）：搜索、单条绑定 / 解绑、批量自动匹配（带确认预览）。

### 2.4 CSP

音频与封面直连 CDN，因此需要放宽两个指令：

```
media-src 'self' https://*.music.126.net
img-src   'self' data: blob: https://*.music.126.net
```

一个通配符同时覆盖音频（`m701/m801.music.126.net`）与封面（`p1/p2.music.126.net`）。
`connect-src` 保持 `'self'` 不变。选择这条而不是由服务器代理音频，
是为了不让 ECS 承担全部音频流量（320kbps ≈ 2.4MB/分钟/人）。
若将来发现 CDN 更换域名导致播放失败，再改为服务器代理。

## 五、后台绑定界面的验证记录（2026-10）

真跑了一遍：临时改站长密码 → 真实登录 → 造 3 首歌 → 匹配 → 绑定 →
查库核对 → 前台取播放地址 → 解绑 → 清理，**29 项断言全过**；
另加 21 项渲染层断言与 17 项 `matchSong` 单元断言。
关键的几条实测结果：

- 演员 - 薛之谦 → 匹配到「演员 — 薛之谦（绅士）」并成功写入
  `apiId=32507038`、封面、歌词 1276 字、专辑「绅士」
- 起风了 - 冯沁苑 → 认作合法别名，匹配到「冯沁苑(买辣椒也用券)」
- 晴天 - 周杰伦 → `confidence=low`、**不绑定**、标记 `nomatch`，
  且仍有候选供人工挑选（符合「只给外链、不绑翻唱」的决定）
- 单首歌的播放地址是按需现取的签名地址：两条不同的歌各拿到不同 URL
- 未绑定的歌 `/api/music/play` 返回 **409** 并带上外链，前端据此退到「去别处听」
- `matchSong` 在「原版被压在候选第 5 位」的构造样例里能正确挑出原版；
  「周杰伦.」「周杰伦♚」「周杰伦的歌」「HF薛之谦」「Jay」全部判为不可信

**验证时踩到的两个坑**（记下来免得重复）：

1. 断言封面时我用了自己拼的 `p2/{picId}.jpg`，且判定条件是
   「URL 字符串出现在页面里」→ 看着通过了，其实那个地址是 **404**。
   **断言必须用接口真实返回的地址，并且最好验证它真的能取到图。**
2. 前台卡片墙在 SSR 里**只有折叠状态的歌手卡片**，歌曲列表要点击才展开渲染，
   所以行内的「待绑定」徽标在首屏 HTML 里根本不存在。
   对这类内容的断言要改成查 flight 数据（如 `apiId`）或查前端产物，
   不能断言首屏 HTML 里有这段文字。

**这一轮验证真抓出来的三个功能缺陷**（都是先写断言、才发现的）：

1. **`SongBindSchema` 的 `items` 写死了 `.min(1)`** → 后台「标记无原版」
   这个只标记、不绑定的动作会被 **400 拒掉**，按钮点下去其实是坏的。
   改成 `items` 允许空数组 + `refine` 保证「两者不能都空」。
2. **`/match` 根本没排除 `matchStatus = "nomatch"` 的歌** →
   「标记后不再重复搜它」这句当时是**假的**，标记只影响计数显示。
   加过滤时又差点踩第二个坑：`{ not: "nomatch" }` 在 SQL 里
   `NULL <> 'nomatch'` 结果是 **NULL 而不是 true**，会把所有「没搜过」
   的新歌一起滤掉（自动匹配直接废掉）。必须写成显式 OR。
3. **`/unbind` 顺手把 `matchStatus` 也清了** →
   「清除全部绑定」一键就把当初判定无版权的结论抹掉，下次又白搜一遍。
   「有没有绑定」与「搜过有没有原版」是两件事，不该一起清。

**仍未在真实浏览器里听过声音**（见交接文档 7.6）：播放、拖动进度条、
歌词滚动、以及「地址失效后自动重取并续播」都是浏览器行为，需要人工点一遍。

## 六、切歌延迟与竞态优化（本轮）

站长反馈两个现象：**切歌有时延迟**、**切太快会出现「界面到下一首、声音还是上一首」**。

### 6.1 竞态根因（实测确认，不是玄学）

`player-context.tsx` 的 `start()` 里：

```ts
setCurrent(song)              // ① 立刻改 UI 显示的曲目
const res = await fetch(...)  // ② 等取播放地址（网络往返，几百毫秒）
audio.src = data.url          // ③ 才真正换音源
```

**`setCurrent` 在 await 之前、`audio.src` 在 await 之后。** 于是取地址的那几百毫秒里，
界面已经显示新歌、音源却还是旧的 —— 这就是「界面到下一首、声音还是上一首」。

连点「下一首」时更糟：多个 `start()` 叠着跑，而**响应回来的顺序不保证与发出顺序一致**，
晚到的旧响应会把 `audio.src` 改回去，造成界面与声音彻底错位。

**修法（两道）**：

1. **请求代际标记**：每次 `start()` 领一个自增序号，每个 `await` 回来先确认
   「我还是最新那次吗」，不是就直接放弃（不碰 audio、不改任何 state）。
   同时用 `AbortController` 取消上一个未完成的请求。
2. **切歌瞬间先 `pause()`**：消掉「界面已切、旧歌还在响」那个窗口 ——
   先停再取，「看到什么就听到什么」。

另外修掉三处相关缺陷：

- `finally { setLoading(false) }` 每个请求都执行 → 旧请求结束会把新请求的转圈关掉。
  改为只有最新那次能改 `loading`。
- 旧请求的响应仍会写 `setError` → 可能弹出与当前歌无关的错误。同样由代际挡掉。
- `play()` 的 `AbortError` 被当成播放失败：切歌本来就会打断上一个 `play()`，
  必须静默忽略（否则每次连续切歌都报一次「无法播放」）。

### 6.2 延迟：先量化两段，再决定优化哪段

| 阶段 | 能优化吗 |
| :--- | :--- |
| ① 请求 `/api/music/play` 取签名地址 | ✅ 预取 |
| ② 浏览器加载音频本身（CDN 重定向 + 缓冲） | ⚠️ 受限于第三方 CDN 速度 |

**预取下一首**：开始播一首之后就顺手取下一首的地址缓存起来，
用户点「下一首」时直接命中，省掉那段接口往返。

三个限制（都是必要的）：

- **只预取 1 首**。第三方限流 60 次 / 5 分钟，项目自设闸门 45 次 ——
  预取太激进会把配额烧光，反而让真正要播的那首拿不到地址。
- **只在成功开播之后预取**。失败时预取等于白耗配额。
- **只取地址、不预加载音频数据**。`preload="none"` 的「省流量」意图保留下来了。

> ⚠️ 预取算「下一首」必须用 **`peekNextSong`**，不能直接调 `resolveStep`。
> 后者在随机模式下会把当前歌压进 `history` —— 那等于预取顺手「前进」了一步，
> 之后真正点下一首算出来的歌与预取的不是同一首（预取永远打不中），
> 随机播放的返回顺序也会错乱。**我第一版就是这个错误**，
> 所以专门抽了 `peekNextSong` 并在测试里断言「只看不改」。

### 6.3 失败分流：没版权直接跳，限流才重试

服务端 `/api/music/play` 现在返回一个**结构化错误码** `code`，
播放器据此决定「重试还是换歌」——而不是靠匹配中文文案（文案一改就静默失效）：

| code | 归类 | 处理 |
| :--- | :--- | :--- |
| `not_playable` / `url_unavailable` / `bad_request` | 永久（没版权等） | 立刻换下一首 |
| `quota_exhausted` / `upstream_error` / `rate_limited` | 暂时 | 退避重试最多 2 次，仍失败才换 |
| `unauthorized` | 永久 | **停止**（继续跳只会一路跳到上限） |

- 退避是**指数**的（0.6s → 1.5s）：立刻重试对限流场景只会更糟。
- **连续跳过上限 5 首**：防「队列里每首都播不了」时一路跳到底、把配额烧光。
- `quota_exhausted` 直接停：换下一首同样取不到地址，跳了也没用。

### 6.4 加载动画与「静默跳过」的 UX 问题

`loading` 状态本来就存在，但两个组件**从没渲染过**（只做 `disabled={loading}`），
所以延迟期间用户看到的是「点不动但没反应」。现在：

- 播放按钮在加载时换成旋转图标，`aria-label` 变成「加载中」
- 底部条的封面压暗 + 中心转圈；沉浸层在唱盘外套一圈细的旋转弧
- 曲目信息位置显示「正在加载…」

**顺带发现并修掉一个真问题**：永久失败（没版权）会直接换下一首，
而 `start()` 开头会 `setError(null)` —— 逐首报错的话那句话会在下一首开始加载的
瞬间被清掉，**用户什么都看不到**（实测诊断确认：跳到了下一首、页面上零提示）。

改成**累积跳过、等落定后统一说明**：

- 一直跳 → 到上限时提示「连续 N 首都无法播放，可能音乐接口出了问题」
- 跳着跳着播上了 → 提示「已跳过 N 首无法播放的歌：…」
- 一次就成功 → 没有这条提示

这条提示用**灰色**（新增独立的 `notice` 状态），不是红色 ——
它不代表故障（当前这首正在正常播），用红色会让人以为出错了。

### 6.5 本轮的测试与一处诚实的限制

| 脚本 | 覆盖 | 结果 |
| :--- | :--- | :--- |
| `npm run music:order-test` | `play-order` 纯函数，含 `peekNextSong` 的「只看不改」 | 29 项全过 |
| `npm run music:error-code-test` | `/api/music/play` 各失败场景的 code 分类 | 12 项全过 |
| `npm run music:ui-check` | 真实浏览器：竞态、加载状态、失败分流 | 核心竞态断言全过；5 项因时序敏感未过（见下） |

**`music:ui-check` 里没过的 5 项不是实现缺陷**，是测试环境的时序敏感性：

- loading 是**瞬时状态**，`run()` 一次 CDP 往返本身有开销，单点采样抓不到
  （已加 MutationObserver 证实「过程中确实出现过」）
- 失败分流是**链式跳过**，精确编排每一步的时序很脆

**更重要的是这条限制**：headless 里**无法验证「真的出声」**。

- `data:` URI 被应用的 CSP 挡（`media-src 'self' https://*.music.126.net`），
  实测报错 `Media load rejected by URL safety check`（error.code=4）——
  那是**正确的安全设计**，不该为了测试放宽它
- 第三方 CDN 的签名地址本地拿不到（配额 + 网络）
- 试过用 CDP 的 Fetch 域在网络层回真实 WAV 字节（含 206 + Content-Range），
  `<audio>` 仍不播 —— headless 的媒体栈在这个环境里就是不工作

所以测试改为接管 `HTMLMediaElement` 的 `play/pause/src`，让**状态机照常走完**，
只断言可可靠观测的部分（请求序列、`src` 指向、DOM 状态）。
**结论：竞态与状态机已在真实浏览器里验证；「真实出声」仍需人工点一遍。**

## 七、安全加固与随机播放修复（本轮）

### 7.1 随机播放第一首固定（站长反馈）

```ts
// 修复前
function playAll(random: boolean) {
  setMode(random ? "shuffle" : "sequential")
  play(playable[0], playable)   // ← 永远从第 1 首开始
}
```

`random` 只改了「后续怎么走」（模式），**起点写死成 `playable[0]`** ——
所以每次都听到同一个开头，只有后面的歌是随机的。

**修法**：新增 `playShuffled`，从队列里**随机挑一首**当起点，
并**当场**把随机顺序洗好（`buildShuffleOrder` 以被选中的那首为位置 0）。

- 起点不排除「当前正在播的那首」——站长选择纯粹随机
  （代价：连点两次有小概率抽到同一首，1/N）
- 当场洗顺序而不是等第一次点「下一首」才惰性生成：播放列表展示的顺序
  立刻就是真实的随机顺序，不会看着是原始顺序、点一下却跳到别处

三种入口的行为现在区分清楚了：

| 操作 | 起点 | 后续 |
| :--- | :--- | :--- |
| 点「随机播放」 | **随机**（已修） | 随机 |
| 点「播放全部」 | 第一首 | 顺序 |
| 点某首歌 | 那首 | 顺序 |

回归测试：`npm run music:shuffle-test`（8 项，含「旧写法只会出现 1 种起点」的对照）。

### 7.2 🔴🔴 限流可被一个请求头完全绕过（本轮最严重的发现）

```
nginx:  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        → 保留客户端自带的值，再把真实 IP 追加在后面

应用:   getClientIp() 取 XFF 的**第一个**值 → 取到的正是攻击者伪造的那段
```

攻击方式与后果（实际可执行，不是理论）：

```bash
# 每次换一个假 IP，限流永不生效
curl -H "X-Forwarded-For: 1.2.3.4" https://站/api/auth/send-code ...
```

| 受影响 | 绕过后的后果 |
| :--- | :--- |
| 发码的 IP 日限（30 次） | 无限刷发码 → **烧光 Resend 免费额度（100 封/天）**，之后站长自己也发不出验证码 |
| 登录的 IP 限流（30 次/分钟） | 可以**无上限暴力破解**密码 |
| 校验验证码的频率限制 | 可以高频尝试（但「同一码错 5 次作废」仍在兜底） |

**修法（两层都做）**：

1. **Nginx 侧**：`proxy_set_header X-Forwarded-For $remote_addr;` —— 用**覆盖**代替追加，
   客户端伪造的值直接被丢弃。改了 `scripts/https/enable.sh` 模板与 README。
2. **应用侧**：`getClientIp()` 改为按 `TRUSTED_PROXY_HOPS`（当前 1）从**右往左**取，
   再退回 `X-Real-IP`，并对 IP 形状做校验；拿不到时打一条警告日志（每进程一次）。

> 只做 Nginx：配置被回退就立刻失效。只做应用：依赖「最后一跳可信」的假设。
> 两层都要有，这才是纵深防御。

**将来加 CDN / 负载均衡时必须同步改** `TRUSTED_PROXY_HOPS`，
否则会把 CDN 的地址当成客户端 IP —— 所有人共用一个限流桶。这条前提已写进
`rate-limit.ts` 注释与 README。

回归测试：`npm run security:xff-test`（15 项，含「伪造不同前缀仍落到同一个限流桶」）。

#### 7.2.1 上线后的实测结果与一个必须知道的前提

改完部署后实测（用新增的 `/api/diag/client-ip`）：

```bash
# 伪造头已失效 —— 回显的是真实 IP
curl -H "X-Forwarded-For: 1.2.3.4" https://站点/api/diag/client-ip
→ {"clientIp":"223.160.112.252", "raw":{"x-forwarded-for":"223.160.112.252", ...}}
```

**修复确认生效。** 但测试过程中出现过一组**自相矛盾**的结果，值得记下来：

| 测试 | 结果 |
| :--- | :--- |
| 连发 21 次（限流 20 次/小时） | **全部 200**（按理第 21 次该 429） |
| 紧接着连发 31 次 | 第 17 次开始**零散出现 429** |

原因查明了：**客户端的出口公网 IP 在轮换**。连跑 5 次诊断接口，看到：

```
223.160.112.252
223.160.112.252
223.160.113.252   ← 变了
223.160.113.252
223.160.113.252
```

于是 21 次请求被分散到 **2 个限流桶**，每个都没到 20 → 全放行；
后续请求继续累加，2 个桶先后到 20 → 出现零散 429。
**限流一直是正常工作的**，只是被 IP 轮换摊薄了。

> ### 结论：IP 限流本来就是最容易被绕过的一道
>
> 换 IP、换代理、CGNAT、动态公网 IP —— 都能让「按 IP」的闸门失效。
> 所以本站真正的防线是**不依赖 IP 的那些**：
>
> | 闸门 | 限制 | 换 IP 能绕过吗 |
> | :--- | :--- | :--- |
> | 同一邮箱冷却 | 60 秒 | ❌ |
> | 同一邮箱日限 | 10 次/天 | ❌ |
> | 同一验证码错误次数 | 5 次作废 | ❌ |
> | **全站日限** | **80 次/天** | ❌ |
> | **全站月限** | **2500 次/月** | ❌ |
>
> 最坏情况：攻击者轮换 IP 无限刷 → **全站 80 次/天就卡死**，
> 最多烧掉 80 封额度（Resend 免费额度 100 封/天），站长仍有余量。
> 这正是当初加「全站硬闸」的理由（见第 3.6 节）。

**想干净地验证 IP 限流，要从固定 IP 发起**（例如在服务器上直连
`http://127.0.0.1:3000`，不经 Nginx、不受本地网络影响）。

### 7.3 🔴 `retry=1` 能瞬间打光第三方配额

`/api/music/play?retry=1` 会**跳过服务端缓存**直打第三方，而原有的
60 次/分钟限流分不清「正常播放」与「强制刷新」：

```
1 秒内刷 45 次 ?retry=1 → 第三方配额（45 次/5 分钟）当场耗尽
→ 全站接下来 5 分钟谁都听不了歌（包括站长）
```

**这个放大是真实的**：正常播放大量请求都能命中缓存、不消耗配额，
而强制刷新每一次都实打实消耗一次。

**修法**：给 `retry=1` 单独一道 **3 次 / 5 分钟**的限流。
正常用户的地址失效是偶发事件（暂停很久再继续），3 次足够；
最坏情况从「45 次打光配额」压到「3 次」。

### 7.4 上游响应形状校验

原先只判 `url.length === 0`，于是两种情况被混为一谈：

| 上游返回 | 真实含义 | 修复前 | 修复后 |
| :--- | :--- | :--- | :--- |
| `{ "url": "" }` | 该音源确实没有这首 | 没版权 | `url_unavailable`（永久，换歌） |
| `{}` / 缺失字段 | **上游协议变了** | ❌ 也说成「没版权」 | `upstream_error`（暂时，值得重试） |

修之前的后果：上游一改字段，表现为「这首歌突然没版权了」，
排查时完全想不到是上游协议问题。现在三处（播放地址 / 封面 / 歌词）都加了形状校验。

回归测试：`npm run music:upstream-test`（17 项，用 mock 构造各种畸形返回）。

### 7.5 验证码发码的并发缺口

`sendCode` 里「检查冷却」与「写库」之间**不是原子的** ——
两个并发请求可以同时通过检查，于是**发出两封邮件、占掉两次配额**，
而 60 秒冷却的本意正是「只发一封」。

**修法（两道）**：

1. 按「邮箱 + 场景」粒度的**进程内互斥锁**，把「检查 → 写库」整段串行化
2. 写库后**再确认一次**「最新一条是不是我」，不是就删掉自己这条并放弃发送
   （兜住跨进程并发；进程内锁管不到多实例）

> 局限已写进代码注释：进程内锁只在单实例下有效。若将来改 PM2 cluster，
> 要换成数据库约束（例如「同一 email+scene 只允许一条未消费记录」的唯一索引）。

回归测试：`verify-code-test` 第 16 节（并发 5 次只有 1 次成功、只发出 1 封）。
