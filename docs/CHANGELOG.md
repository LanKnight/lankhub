## v0.7.0 — 2026-10-07

### ⚠️ 破坏性变更：歌单删掉外链字段，录入改成「搜索添加」

**适用对象：所有升级上来的库。** ⚠️ **这一步需要 `--accept-data-loss`。**

歌单不再有外链字段，`Song.link` 被删除。录入方式从「粘贴一批歌名歌手」
改成**搜索添加**：搜到结果后挑一个版本，歌手、专辑、封面与歌词都由搜索结果的 ID
带出来，不需要手工录，也不需要自己分类。

**升级步骤**（在服务器上执行一次）：

```bash
git pull
npx prisma db push --accept-data-loss   # 删列，必须显式接受
npm run update                          # 之后照旧一键更新
```

> ⚠️ **`Song.link` 里的数据会永久丢失。** 删列不可逆。
> 升级前可以先看看有没有数据，需要的话自行留档：
>
> ```bash
> sqlite3 dev.db "SELECT id, title, artist, link FROM Song WHERE link IS NOT NULL;"
> ```
>
> （站长已确认线上歌单没有任何一首歌填过外链，所以实际没有数据损失。）

其它改动：

- 新增「搜索添加」对话框：填歌名（歌手可选）→ 结果列出歌名/歌手/专辑 →
  `添加并绑定` 或 `只加入歌单`。没有想要的版本就什么都不点，不会留下半条记录
- 结果里把歌名与歌手对不上的标为**「疑似翻唱」**，但**不隐藏** ——
  选哪个版本仍然由人决定
- 结果按「最可能是原版」排序（歌手可信且歌名精确相同的排最前）
- 歌单里若已有同名同歌手的歌，**不重复建记录**，只补绑定
- 后台删掉「批量粘贴导入」：接口 `POST /api/admin/music/import` 与
  解析器 `src/lib/music.ts` 一并删除；`SongImportSchema` 与 `SongLinkSchema` 删除
- 手动添加保留为精简版（只有歌名 + 歌手），留给源站确实没收录的歌
- 前台未绑定的歌**置灰不可点**，标「本站无此版本」；
  播放失败不再有「去别处听」的退路（歌单已无外链）
- **`/api/admin/music/bind` 新增一道校验**：提交的版本必须来自当前搜索结果。
  理由是后台允许改歌名与歌手，旧对话框可能拿着过期结果提交，
  会把 A 歌的播放 ID 写进 B 歌（前台会放出一首毫不相干的歌）。
  代价是每个 item 多花 1 次搜索配额，同批同名同歌手的会去重只搜一次

> 新增的接口 `POST /api/admin/music/add` 只负责建记录（幂等），绑定仍走原有的 `/bind`。

## v0.6.1 — 2026-10-07

### 修复：后台歌单绑定界面接线，并修掉匹配与标记的三个缺陷

commit `d858f1d`

**适用对象：已升级到 v0.6.0（清弦在线播放）的库。** 全新部署不需要任何额外操作。

- 后台 `/admin/music` 现在有绑定状态徽标、封面缩略图、`搜索绑定` / `解绑`、
  配额剩余、`自动匹配未绑定的歌`、`清除全部绑定`
- 匹配算法改为**本地重排**（不再依赖接口的相关度顺序），
  实测「大鱼 - 周深」的可信原版排在候选第 8 位、前面 7 条都是翻唱，
  照顺序取就会绑错
- 修掉三个缺陷：
  - `SongBindSchema` 的 `items` 写死 `.min(1)`，导致「只标记无原版」被 400 拒掉
  - `/match` 没排除 `matchStatus = "nomatch"` 的歌（过滤必须用显式 OR，
    因为 SQL 里 `NULL <> 'nomatch'` 是 NULL 而不是 true，会把所有新歌一起滤掉）
  - `/unbind` 顺手清掉 `matchStatus`，会让「清除全部绑定」一键抹掉「源站无原版」的结论

> 本次**没有 schema 变更**，`npm run update` 可以直接跑。

## v0.5.0 — 2026-10-06

### 新功能：相册的「清弦」改造成歌单页 /music，支持批量粘贴导入

commit `b583d36`

**适用对象：所有升级上来的库**（若库里从未有过 `category = 'music'` 的照片，可忽略最后一条）。

「清弦」原本是相册里的音乐分类，因为音乐照片太少，已改造成**歌单页 `/music`**。

- `/photos/music` 会 **308 永久重定向**到 `/music`，旧链接与书签不会失效
- 相册分类从 6 个变成 5 个，「清弦」这一格改由首页「兴趣爱好」直接指向 `/music`
- 歌单存在新表 `Song` 里，`npm run update` 里的 `db:push` 会自动建表，
  **这一步没有数据丢失风险，不需要 `--accept-data-loss`**
- 如果库里还残留着 `category = 'music'` 的照片（已被清空的话可忽略），
  它们不会再被任何页面展示，可自行删除：
  `sqlite3 dev.db "DELETE FROM Photo WHERE category = 'music';"`

歌单支持**批量粘贴导入**：在 `/admin/music` 选「批量粘贴」，每行一首、写成
`歌名 - 歌手`（也认 `–`、`—`、`|`、制表符，以及行首的 `1.`、`-` 之类的列表标记；
两侧的《》「」会自动去掉）。粘贴后会先给出预览，解析不了的行会单独列出来并说明原因，
导入时还会跳过已存在的同名同歌手条目。

### 清理与技术债：zod schema 真正生效 + 上线前数据预检

commit `1307e3f`、`71258d2`

**适用对象：所有升级上来的库，尤其是历史数据较多的库。**
必须先跑一次预检，否则可能出现「能看不能存」的历史记录。

**接口的请求校验统一收进了 zod schema**，并新增了 `npm run db:check-limits` 预检。

- 起因是 `src/lib/validations.ts` 里有 4 个 schema 定义了却从没被引用，
  而对应的接口各自手写了一套平行规则。现在评论 / 合集 / 简历 / 分页四组接口都真正用上了它们
- **代价是出现了一批过去不存在的长度与格式限制**：这些限制只作用在请求上，
  **不会改动任何已有数据**，但如果某条历史记录违反了新规则，它就会「能看不能存」——
  在后台点保存永远失败。**上线后先跑一次 `npm run db:check-limits`** 即可查出
- 那个脚本直接复用 `src/lib/validations.ts` 里的 schema，不另抄一份限制，
  所以以后改了 schema、预检会跟着变，不会失真
- 另外把「可空字段」对齐了：`Collection.coverImage`、`Article.summary` 这些在库里是 `null` 的列，
  schema 现在同时接受 `null`，否则把数据库记录原样回传的客户端会被 400

同一轮还清理了几处历史遗留：

- 删掉 `scripts/deploy.sh`（WSL 本地构建部署，服务器 IP 一直是占位符，已被 `npm run update` 取代）
- 删掉 `prisma/dev.db`（0 字节空壳，真正的库是根目录的 `dev.db`）
- 删掉两个无人调用的接口 `/api/collections` 与 `/api/collections/[slug]`
  （前端合集页是服务端直接查库的；它们本来也不泄漏草稿，所有查询都过滤了 `published`）
- sitemap 补上 5 个相册分类页（此前只有固定几个路由）
- 后台侧栏改为由服务端传入会话，不再先渲染一个空的 `<nav>` 再水合

## v0.4.0 — 2026-10-05

### ⚠️ 破坏性变更：昵称唯一约束（不能直接跑 npm run update）

commit `a3fdc19`

**适用对象：只对「库里已有数据、且昵称可能有重复或损坏」的库有意义。**
⚠️ **这一条已不再适用于当前版本**——唯一约束早在 10-05 就已加上，
如果你是在此之后才建立的库（或用 `npm run setup` 全新初始化），
**直接跑 `npm run update` 即可，不需要下面任何步骤**。

> ⚠️ **本次升级不能直接跑 `npm run update`，会中途失败。**
>
> 用户昵称（`User.name`）加上了唯一约束。Prisma 遇到「给已有数据的列加唯一索引」
> 会先给出数据丢失警告并要求 `--accept-data-loss`，而 `npm run update` 里的 `db:push`
> 没带这个参数，**会在推送数据库那一步中断**。另外如果库里已存在重名昵称，
> 加索引会直接失败，所以必须先把存量昵称整理干净。
>
> 在服务器上按顺序执行一次：
>
> ```bash
> git pull                                        # 先拿到新 schema 与整理脚本
> npm run db:normalize-usernames -- --dry-run     # 先预览会改哪些昵称
> npm run db:normalize-usernames                  # 确认后执行（幂等，可重复跑）
> npx prisma db push --accept-data-loss           # 这一次需要显式接受数据风险
> npm run update                                  # 之后照旧一键更新
> ```
>
> 整理脚本会做的事：去掉首尾空白、把编码损坏的昵称（含 U+FFFD）换成 `user-<id>`、
> 截断到 20 字、给重名依次追加 `-2`、`-3`。跑第二遍会报「无需整理」。

### 新功能：账号设置 /settings 与退出登录入口统一

commit `2ab8d76`

**适用对象：所有人。** 纯前端与路由调整，无 schema 变更。

同一版本还新增了 `/settings`（账号设置）：**所有登录用户**都能改自己的昵称与密码。
