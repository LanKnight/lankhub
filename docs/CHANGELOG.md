## v0.9.2 — 2026-10-09

### 修复：唱片暂停不停转、歌词不滚动不居中；唱片放大；歌词入口放回播放条

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**，`npm run update` 可以直接跑。

#### 修复一：暂停后唱片还在转（CSS 规则顺序问题）

`animation-play-state` 原本靠额外一个 Tailwind 任意属性
`[animation-play-state:paused]` 实现，与 `.animate-disc-spin` **特异性相同（都是单类）**，
谁生效完全取决于打包顺序。实测产物里：

```css
.\[animation-play-state\:paused\]{animation-play-state:paused}   /* 先 */
.animate-disc-spin{animation:24s linear infinite disc-spin}      /* 后 → 胜出 */
```

后出现的那条 `animation` **简写**把 `animation-play-state` 覆盖掉了，所以唱片停不下来。

**修法**：把暂停收进同一个 class —— `.animate-disc-spin.is-paused`。
同一个类里声明，顺序就不可能打架。

#### 修复二：歌词完全不滚动、也不居中（容器高度自适应）

歌词容器的 class 是 `flex-1` 配 `overflow-y-auto`，但**没有 `min-h-0`**。
在 flex column 里，`flex-1` 的默认 `min-height:auto` 会让元素**被内容撑开**而不是
滚动 —— 于是容器根本没有溢出，`scrollTo` 什么也没做。

另外留白不足：即使能滚，滚到顶就是极限，**第一行与最后一行永远无法居中**。

**修法**：

- 容器加 `min-h-0`，让它真正填满可用空间并产生溢出
- 上下留白按**实测容器高度的一半**动态计算（`ResizeObserver` 跟随尺寸变化），
  这样任何一行都能滚到正中
- 改用 `scrollIntoView({ block: "center" })`，不再自己算偏移
- 切歌时也要重新居中（依赖里带上 `lyricLines`，否则「都是第 0 行」时 effect 不重跑）
- **底部那个歌词抽屉有完全相同的两个 bug，一并修掉**（`h-56` 配 `py-[7rem]`）

#### 改进：唱片放大

桌面从 `16rem / 18rem` 放大到 `26rem / 30rem`；窄屏从 `10rem / 12rem` 到 `13rem / 16rem`。
**只在桌面放到最大** —— 窄屏是上下堆叠，唱片太大会把歌词挤没。

#### 改进：歌词入口放回播放条

删除沉浸层里那行「在页面内看歌词」小字（站长反馈太隐蔽），
在播放条上加回**独立的歌词按钮**，于是两个入口都能直达：

- `ListMusic` 图标 → 底部歌词抽屉（边看歌单边看歌词）
- `ChevronUp` 图标 → 沉浸式全屏

#### 验证方式的一个改进

上一轮漏掉「暂停后唱片还在转」，根因是我**只验证了源码里写了 `[animation-play-state:paused]`，
没验证构建产物里它是否真的生效**。这一轮的断言直接读 `.next` 里的 CSS，
比对两条规则的**先后位置**，并确认旧写法已从产物里消失。

## v0.9.1 — 2026-10-09

### 新功能：沉浸式听歌界面；删除「记住播放状态」

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**，`npm run update` 可以直接跑。

#### 沉浸式听歌界面（全屏层）

点播放条最右侧的 `⌃` 进入：左边旋转的黑胶唱片（封面在中心圆标上）、右边歌词、
底部一条控制（进度条 + 上一首/播放/下一首 + 模式 + 播放列表）。

- **桌面左右分栏；窄屏自动上下堆叠**（唱片在上、歌词在下），否则右栏会被挤成一条缝
- 唱片**播放时旋转、暂停时停转**；黑胶与纹路纯 CSS 画，不引外部图片
- 歌词行级高亮 + 平滑滚动居中
- 键盘：`Esc` 退出、`←`/`→` 切歌、`空格` 播放/暂停
- 打开时锁住背景滚动；带 `role="dialog"` / `aria-modal`
- 尊重 `prefers-reduced-motion`：**显式**加了一条关掉 `disc-spin` 的规则
  （只靠全局那条降级规则不够，见下）

#### ⚠️ 关键约束：它是全屏层，不是新路由

播放器（唯一的 `<audio>` 元素）挂在 `/music` **页面内部**：

```tsx
// src/app/music/page.tsx
<PlayerProvider>
  <ArtistGrid groups={groups} />
  <PlayerBar />
</PlayerProvider>
```

因此**换成另一个路由（如 `/music/immersive`）会卸载这棵子树 → `<audio>` 被销毁 → 歌当场停掉**。
这不是取舍，是机制。所以沉浸式做成了同一页面上的全屏层。

- 代价：没有独立 URL，浏览器后退键不会「退出沉浸式」——所以给了关闭按钮与 `Esc`
- 若将来想让「切到别的页面音乐也不停」，需要把 `PlayerProvider` 提到根布局，
  那是另一个需求，见 `docs/HANDOVER.md` 第 16 节

#### 删除「记住播放状态」

v0.9.0 加的 localStorage 记忆（模式 / 当前曲 / 进度）**整个删掉**。
站长反馈「刷新后恢复且处于暂停」没用 —— 刷新后本来也得手动点一次播放，
不值得为此维护一套持久化。连带删掉的还有：lazy initializer 读初值、写盘定时器、
以及为了「恢复当前曲」而引入的 state 与 `pendingPosition`。

#### 顺手做的小事

- 抽出 `ModeButton`：底部播放条与沉浸层各要一个，各写一遍的话哪天加第四个模式就会漏改一处
- 底部那个歌词抽屉**没有删**，仍在沉浸层底部的「在页面内看歌词」入口后面
- 一个容易漏的降级细节：全局的 `prefers-reduced-motion` 规则只把
  `animation-duration` 压成 0.01ms，`infinite` 动画会变成**极快空转**。
  所以额外写了一条 `.animate-disc-spin { animation: none !important }`，
  让唱片在降级模式下就是一张静止的唱片

## v0.9.0 — 2026-10-09

### 新功能：播放全部、三种播放模式、播放列表面板

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**，`npm run update` 可以直接跑。

#### 卡片墙上方新增「播放全部 / 随机播放」

把**所有歌手的可播歌曲**合成一个队列，因此可以跨歌手连着放
（在此之前，点某首歌的队列只在那位歌手内部，放完就在原地打转）。

- 队列**只收可播的歌**（`apiId` 有值），并明确标出「N 首暂不可播，已跳过」。
  否则「下一首」会停在一首放不出声的歌上
- 不可播的歌仍然**显示**（置灰），不隐藏

#### 底部播放条

- **播放模式**：一个按钮循环切换 `顺序播放 → 单曲循环 → 随机播放`
  - 顺序播放：放完最后一首**就停**（刻意不做「列表循环」，站长没要这个模式）
  - 单曲循环：**自动播完**才重播同一首；手动点「下一首」仍然换歌
  - 随机播放：先洗好顺序再顺着走，**一轮内每首恰好一次**；
    「上一首」走播放历史，所以是**真的回到刚才那首**
- **播放列表**：向上弹出，高亮正在播放的那首，点任意一首跳播
- **歌词抽屉**改为与播放列表**互斥**（两者位置重叠，同时开会叠在一起；
  若歌词开着时打开列表，列表会自动抬高避让）

#### 记住播放状态

模式与当前曲目存进 `localStorage`，下次进站恢复模式、曲目与进度。
刻意**不自动播放**：浏览器会拦截没有用户手势的自动播放，
只会留下一个看起来坏掉的播放条。写入包在 `try` 里，隐私模式下静默失败。

#### 顺手做的重构与修复

- `PlayerBar.tsx`（285 行）拆成四个文件：`PlayerBar` / `LyricsDrawer` /
  `QueuePanel` / `play-order.ts`（纯函数）
- 修掉 `react-hooks/set-state-in-effect` 与 `react-hooks/refs` 两处告警：
  持久化改用 lazy initializer 读初值，恢复当前曲改用「渲染期调整 state」的官方模式
- 新增单元验证 `scripts/_play-order-unit.mts` 的方式：把「下一步是哪首」抽成
  纯函数 `resolveStep`，于是 3 个模式 × 前进/后退的各种边界都能直接跑断言
  （这段逻辑靠手点根本点不全，出错时表现为「偶尔跳过一首」这种难复现的现象）

## v0.8.0 — 2026-10-08

### 新功能：听歌要求登录 + Nginx 前置限流

**适用对象：所有人。** 纯代码与配置改动，**没有 schema 变更**，
`npm run update` 可以直接跑。

#### 听歌要求登录

- `/music` 未登录会跳到 `/auth/login?callbackUrl=/music`（登录后跳回）。
  登录校验放在**查库之前** —— 否则「要求登录」只是前端遮罩，直接请求照样能读全量歌单
- `/api/music/play` 未登录返回 **401**（不是 403，便于前端区分「该登录」与「没权限」）
- `/music/disclaimer` **保持公开**：免责声明是给版权方与未登录访客看的
- 播放接口的按 IP 限流从 30 次 / 分钟放宽到 **60 次 / 分钟**：
  播放已经要登录了，30 对正常使用偏紧（连点几首、进度条重试都可能撞上）

> ⚠️ **这是门槛，不是访问控制。** 站点注册是公开的，任何人注册后即可收听。
> 它挡的是「路过的人、爬虫、懒得注册的人」，并让播放行为能对应到账号。
> 要真正限住人，需要先关闭公开注册 —— 站长选择了保留开放注册。
>
> **实际收益**：未登录的请求在消耗第三方配额**之前**就被挡掉了。

#### Nginx 前置限流（新增一层）

README 的 Nginx 配置新增 `limit_req_zone` / `limit_conn_zone`：
全站 10r/s（burst 20）、`/api/music/play` 2r/s（burst 5）、并发连接 20/5，
超限返回 429。README 同时给出了**验收方法**，其中包含
「正常浏览必须不被误伤」这一条 —— 误伤访客比限流失效更值得警惕。

> ⚠️ 配置里 `proxy_set_header X-Forwarded-For` **不能少**：
> 应用靠它识别客户端，一旦缺失会回退成 `127.0.0.1`，
> 所有访客共用一个限流桶 —— 要么互相误伤、要么限流整体失效，界面上看不出来。

#### 记录一个没做、但将来要注意的坑

`canAccessAdmin()` 的判据是「拥有任意一个权限码」，而 `PERMISSIONS` 现在全是内容权限。
**将来若要加非内容类权限（播放、下载…），必须先把 `canAccessAdmin` 改成只认内容权限**，
否则那个账号会静默获得进入 `/admin` 的资格。
本轮没有新增权限码（听歌只要求登录），所以没有触发；警示已写进 `src/lib/permissions.ts` 顶部。

## v0.7.0 — 2026-10-07

### ⚠️ 破坏性变更：歌单删掉外链字段，录入改成「搜索添加」

**适用对象：所有升级上来的库。** ⚠️ **这一步需要 `--accept-data-loss`。**

歌单不再有外链字段，`Song.link` 被删除。录入方式从「粘贴一批歌名歌手」
改成**搜索添加**：搜到结果后挑一个版本，歌手、专辑、封面与歌词都由搜索结果的 ID
带出来，不需要手工录，也不需要自己分类。

**升级步骤**（在服务器上执行一次）：

```bash
git pull
npx prisma db push --accept-data-loss   # 删列，必须显式接受
npm run update                          # 之后照旧一键更新
```

> ⚠️ **`Song.link` 里的数据会永久丢失。** 删列不可逆。
> 升级前可以先看看有没有数据，需要的话自行留档：
>
> ```bash
> sqlite3 dev.db "SELECT id, title, artist, link FROM Song WHERE link IS NOT NULL;"
> ```
>
> （站长已确认线上歌单没有任何一首歌填过外链，所以实际没有数据损失。）

其它改动：

- 新增「搜索添加」对话框：填歌名（歌手可选）→ 结果列出歌名/歌手/专辑 →
  `添加并绑定` 或 `只加入歌单`。没有想要的版本就什么都不点，不会留下半条记录
- 结果里把歌名与歌手对不上的标为**「疑似翻唱」**，但**不隐藏** ——
  选哪个版本仍然由人决定
- 结果按「最可能是原版」排序（歌手可信且歌名精确相同的排最前）
- 歌单里若已有同名同歌手的歌，**不重复建记录**，只补绑定
- 后台删掉「批量粘贴导入」：接口 `POST /api/admin/music/import` 与
  解析器 `src/lib/music.ts` 一并删除；`SongImportSchema` 与 `SongLinkSchema` 删除
- 手动添加保留为精简版（只有歌名 + 歌手），留给源站确实没收录的歌
- 前台未绑定的歌**置灰不可点**，标「本站无此版本」；
  播放失败不再有「去别处听」的退路（歌单已无外链）
- **`/api/admin/music/bind` 新增一道校验**：提交的版本必须来自当前搜索结果。
  理由是后台允许改歌名与歌手，旧对话框可能拿着过期结果提交，
  会把 A 歌的播放 ID 写进 B 歌（前台会放出一首毫不相干的歌）。
  代价是每个 item 多花 1 次搜索配额，同批同名同歌手的会去重只搜一次

> 新增的接口 `POST /api/admin/music/add` 只负责建记录（幂等），绑定仍走原有的 `/bind`。

commit `d858f1d`

**适用对象：已升级到 v0.6.0（清弦在线播放）的库。** 全新部署不需要任何额外操作。

  - `/unbind` 顺手清掉 `matchStatus`，会让「清除全部绑定」一键抹掉「源站无原版」的结论

> 本次**没有 schema 变更**，`npm run update` 可以直接跑。

## v0.5.1 — 2026-10-06

## v0.4.0 — 2026-10-05

### ⚠️ 破坏性变更：昵称唯一约束（不能直接跑 npm run update）

commit `a3fdc19`

**适用对象：只对「库里已有数据、且昵称可能有重复或损坏」的库有意义。**
⚠️ **这一条已不再适用于当前版本**——唯一约束早在 10-05 就已加上，
如果你是在此之后才建立的库（或用 `npm run setup` 全新初始化），
**直接跑 `npm run update` 即可，不需要下面任何步骤**。

> ⚠️ **本次升级不能直接跑 `npm run update`，会中途失败。**
>
> 用户昵称（`User.name`）加上了唯一约束。Prisma 遇到「给已有数据的列加唯一索引」
> 会先给出数据丢失警告并要求 `--accept-data-loss`，而 `npm run update` 里的 `db:push`
> 没带这个参数，**会在推送数据库那一步中断**。另外如果库里已存在重名昵称，
> 加索引会直接失败，所以必须先把存量昵称整理干净。
>
> 在服务器上按顺序执行一次：
>
> ```bash
> git pull                                        # 先拿到新 schema 与整理脚本
> npm run db:normalize-usernames -- --dry-run     # 先预览会改哪些昵称
> npm run db:normalize-usernames                  # 确认后执行（幂等，可重复跑）
> npx prisma db push --accept-data-loss           # 这一次需要显式接受数据风险
> npm run update                                  # 之后照旧一键更新
> ```
>
> 整理脚本会做的事：去掉首尾空白、把编码损坏的昵称（含 U+FFFD）换成 `user-<id>`、
> 截断到 20 字、给重名依次追加 `-2`、`-3`。跑第二遍会报「无需整理」。
