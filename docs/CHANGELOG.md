## v0.11.1 — 2026-10-13

### 修复：`https:redirect` 插入跳转导致 `duplicate location "/"`

**适用对象：所有人。** 只改 HTTPS 脚本。

站长执行 `sudo npm run https:redirect` 时报：

```
[emerg] duplicate location "/" in /etc/nginx/sites-enabled/lankhub.xyz:10
nginx: configuration file /etc/nginx/nginx.conf test failed
```

> ✅ **没有造成影响**：`nginx -t` 拦住了、**没有 reload**、并自动还原了配置。
> 站点全程正常。这印证了「语法检查作为硬门槛 + 失败自动回滚」的价值。

#### 根因

我把 301 片段是**插入**在原有的 `location /` **之前**：

```nginx
location / { return 301 https://www.lankhub.xyz$request_uri; }   # 我插的
location / {                                                      # 原来的
    proxy_pass http://127.0.0.1:3000;
    ...
}
```

**nginx 不允许同一个 server 块里出现两个相同的 location** —— 于是 `duplicate location "/"`。

#### 改法：**替换**而不是插入

正确的做法是把原有的 `location /` 块**整段换成** 301。于是需要解决两个问题：

1. **识别整个块的边界** —— 用「去掉空白后的花括号计数」配对，
   而不是只找一行（原来的块是多行、且内部还有 `{}` 嵌套在同级指令里）
2. **撤销时要把原块放回去** —— 不能只删跳转，否则 80 会失去 `proxy_pass` 而返回 **502**

所以新增状态文件：`/etc/nginx/lankhub-state/<配置文件>.redirect-state`，
保存被替换掉的原块。`--undo` 与 `disable.sh` 都靠它**原样放回**。

> 状态文件故意放在 `/etc/nginx/lankhub-state/`，**不在 `sites-enabled/` 里**
> （同 `lankhub-backups`，原因见 v0.11.0：那个目录里任何文件都会被当配置加载）。

#### 顺带加固

- `enable-redirect.sh` 与 `disable.sh` 在 `nginx -t` 前都会**数一下 `location /` 的个数**
  并打印出来；多于 1 个时明确提示「大概率重复」
- 状态文件缺失时，`--undo` 与 `disable.sh` 都会**拒绝执行并提示**，
  而不是静默地把 80 弄成 502

#### 验证

- **端到端 25 项**，用站长真实的 80 配置内容：
  替换后只有 1 个 `location /`、代理块已移除、原块完整存进状态文件（首行 `location / {`、
  末行 `}`、11 行）、幂等（重复执行仍只有一份）、
  **`--undo` 后与原始配置逐字一致**、`disable` 同样逐字还原、
  `nginx -t` 失败时还原并清掉状态文件、没有 443 时拒绝执行、状态文件缺失时拒绝执行
- **真实 nginx 启动验证**：`nginx -t` 通过（旧写法在这里就会报 duplicate location）、
  进程真起来、`http://www.lankhub.xyz/` 返回 **301** 且 `Location: https://www.lankhub.xyz/`、
  **路径与查询串完整保留**（`/foo/bar?x=1`）、https 侧 TLS 与代理都通

## v0.11.0 — 2026-10-13

### 新功能：启用 HTTPS（分两步，带证书校验）

**适用对象：所有人。** 新增脚本，**没有 schema 变更**。不改动任何现有代码。

站点默认跑 HTTP（80）。新增 `scripts/https/` 三个脚本：

```bash
sudo npm run https:on -- --cert /etc/nginx/cert/www.lankhub.xyz.pem \
                         --key  /etc/nginx/cert/www.lankhub.xyz.key
sudo npm run https:redirect    # 验证 https 可用之后再加跳转
sudo npm run https:off         # 回退
```

#### ⚠️ 为什么强制分两步

**这个项目刚因为「跳到一个没人监听的端口」把整站打挂**（v0.10.3）。
所以：

- 第一步 `https:on` **只加 443，不做任何跳转** —— 万一 https 不通，80 仍然可用，
  你不会被锁在外面
- 第二步 `https:redirect` 会**主动检查 443 配置是否存在**，不存在就拒绝执行

`https:redirect` 是**幂等**的（重复执行不会产生重复片段），并且支持 `--undo`。

#### 第一步的校验（任何一项不过都不 reload、自动回滚）

| 检查 | 为什么 |
| --- | --- |
| **证书与私钥配对** | `openssl -modulus` 比对。不配对 nginx 直接起不来 |
| **证书覆盖所有要用的域名** | 解析 `subjectAltName` 逐个核对。不覆盖的域名会报证书错误，且会明确报出是哪个 |
| **443 未被别的程序占用** | 被占用时 nginx 起不来 |
| **证书链段数** | 只有 1 段时警告可能缺中间证书 |
| `nginx -t` | 硬门槛，失败自动回滚 |

#### 生成的 443 配置的要点

- **独立文件** `/etc/nginx/sites-available/zz-lankhub-https.conf`，
  **不改动现有的 80 配置**；软链名以 `zz-` 开头，保证排在站点自己的配置之后加载
- 证书拷到 `/etc/nginx/ssl/`，**私钥权限 600**（原文件不动）
- 转发 `X-Forwarded-Proto $scheme` —— 没有它登录后可能被跳回 http
- 只启用 **TLSv1.2 / 1.3**（覆盖 nginx.conf 里仍开着 TLSv1/1.1 的全局设置）
- HTTP/2 用 `listen 443 ssl http2`（老写法）—— 独立的 `http2 on;` 需要 1.25.1+，
  而线上是 **1.24**
- **故意不含 HSTS**：HSTS 会让浏览器在有效期内强制 https，证书一旦出问题
  访客被硬锁在外面、且无法远程解除

#### 开发中抓到的两个真 bug（都已修）

**① 备份写进了 `sites-enabled/` —— 很危险**

我最初把备份写成 `lankhub.xyz.lankhub-bak.*`，就在 `sites-enabled/` 目录里。
而 nginx 是 `include /etc/nginx/sites-enabled/*` —— **那个目录里任何文件都会被
当配置加载**，备份里同样有 `server` 块，于是会产生**重复的 `server_name`**，
行为不可预测。现在备份统一放 `/etc/nginx/lankhub-backups/`。
（幸好这个 bug 只在本地测试暴露，没上过服务器。）

**② 标记剥离用了行首匹配 → 幂等失效**

剥离跳转片段用的是 `index($0, mark) == 1`（要求标记在行首），
但标记是**缩进**的 → 永远匹配不上 → 剥离静默失败 → **重复执行会插入两份片段**，
`--undo` 也删不掉。改成 range 模式匹配。

#### 验证

- **真实 nginx 启动验证**（不只是语法）：`nginx -t` 通过、进程真起来、
  用自签证书做信任锚 `curl --cacert` **真实校验了证书链与域名匹配**，

## v0.10.3 — 2026-10-13

### 🚨 严重修复：维护模式把整站打挂（HTTP-only 站点被 301 跳到不存在的 443）

**适用对象：所有人。** 站长报告：执行 `maintenance:on` 后**域名直接无法访问**。

#### 事故与根因

维护配置写成：

```nginx
server {
    listen 80;
    server_name www.lankhub.xyz;
    location / { return 301 https://$host$request_uri; }   # ← 全部跳 443
}
server { listen 443 ssl http2; ... }                        # ← 但站点根本没监听 443
```

而站长的站点**只用 HTTP**（`sudo nginx -T` 确认：全局没有任何 `listen 443`、
没有任何 `ssl_certificate`）。于是：

**域名请求 → 匹配维护块 → 301 跳到 443 → 443 是死端口 → 浏览器「无法访问」。**

「用 IP 访问反而正常」的原因是：`server_name www.lankhub.xyz` 匹配不到 IP 请求，
IP 落到了 `default_server`（`root /var/www/html`）—— 症状极具误导性。

**我的错误**：没有先确认站点用的是 HTTP 还是 HTTPS，就按 HTTPS 写了配置，
还加了一条 80→443 的跳转。对 HTTP-only 站点，那条跳转等于**把整站打到死端口上**。

#### 改法：配置改为 HTTP-only

- **只监听 80**，不做任何跳转
- 去掉全部 `listen 443` / `ssl_certificate` / `ssl_dhparam` / `http2` / certbot include
- 去掉 `--cert` 参数（配置里已无任何证书相关内容，留着只会误导）
- 每次 `maintenance:build` 都会**打印一行警告**：这是 HTTP-only 配置，
  若将来改用 HTTPS 必须补 443 块，**不要直接让 80 跳 443**

#### 顺带修复：`server_name` 只覆盖了一半域名

原来只写 `www.lankhub.xyz`，于是访问 **`http://lankhub.xyz/`（不带 www）**
会落到站点自己的 server 块、看到**正常页面** —— 维护模式只挡了一半。
现在生成 `server_name www.lankhub.xyz lankhub.xyz;`（去重，`--domain` 传任意一个都对）。

#### 顺带修复：两个软链命名导致 `maintenance:off` 不生效

维护软链名 = 源文件名，历史上源文件叫过 `lankhub-maintenance.conf`。
环境里可能**同时残留两个软链**，而关闭脚本只删一个 →
**关了维护但仍显示维护页**（站长遇到的正是这个：`off` 之后域名还是打不开）。

现在三个脚本都同时处理两个名字：

- `disable.sh` 两个都删，并在删除数 > 1 时提示「之前存在重复软链」
- `status.sh` 会检测并**告警重复软链**（Nginx 会加载重复的 server 块）
- `enable.sh` 检测到已开启时**指出具体是哪个名字残留**，并提示先执行关闭脚本

> 顺带清掉一段**永远走不到的死代码**：我原先在 `enable.sh` 里加了「自动清理
> 另一种命名残留」，但它位于「已开启则退出」检查**之后** —— 那段执行不到。
> 测试用例把它暴露了出来。清理两种命名是 `disable` 的职责。

#### 验证（用真实 nginx 复刻站长的完整环境）

搭建了与他服务器一致的三个 server 块（`default_server` + 主站块 + 维护块），
并用 `curl -H 'Host: ...'` 分别验证：

| 请求 | 结果 | 期望 |
| --- | --- | --- |
| `Host: www.lankhub.xyz` | **503** + 维护页 | ✅ 且**响应头里没有跳 https 的 Location** |
| `Host: lankhub.xyz`（不带 www） | **503** + 维护页 | ✅ |
| `Host: 1.2.3.4`（IP） | **200** 默认页 | ✅ 未受影响 |
| `https://127.0.0.1/` | 无响应 | ✅ 与线上一致——正因如此，任何 80→443 跳转都会打挂站点 |

另加静态检查：维护配置的**指令行**里不得出现 `listen 443` / `ssl_certificate` /
`return 301` / `http2` / `letsencrypt`。

开关脚本端到端 **22 项**全过，含软链双命名的三种场景与 `nginx -t` 失败回滚。

#### 顺带修掉一个脚本自身的 bug

`enable.sh` 里读证书/域名/日志路径的 `grep` **没有 `|| true`**。

### 修复：维护配置在 Nginx 1.24 上语法报错（`http2 on;` 不被支持）

**适用对象：所有人。** 只改了生成的 Nginx 配置模板。

站长在服务器上执行 `sudo npm run maintenance:on` 时报错：

```
[emerg] unknown directive "http2" in /etc/nginx/sites-enabled/lankhub-maintenance:36
nginx: configuration file /etc/nginx/nginx.conf test failed
```

**原因是我按本机版本写了配置**：`http2 on;` 是 nginx **1.25.1** 才引入的独立指令，

listen 443 ssl http2;
listen [::]:443 ssl http2;

这种形式 **1.9.5 起就支持，1.25.1+ 也仍然可用**，是唯一两边都通吃的写法
（1.30 上只会给一条 deprecation 警告，不是错误；实测 HTTP/2 仍正常协商为 `2`）。

> ⚠️ **回滚机制按设计工作了**：语法检查没过，脚本**没有 reload**，
> 并自动删掉了软链 —— 站点全程未受影响。这正是当初把 `nginx -t` 设成硬门槛的意义。

#### 顺带补强

- `build.mjs` 找不到维护图时，现在会**列出 `docs/photo/` 里实际有什么文件名**，

- 校验脚本新增**「模拟 nginx 1.24」的静态检查**：配置里若出现

#### 教训

**「本机验证通过」不等于「线上通过」，当两边软件版本不同时尤其如此。**
以后写 Nginx 配置要先问版本（`nginx -V`），或者直接用**跨版本兼容**的写法。

## v0.10.0 — 2026-10-13

### 新功能：维护模式（临时挂出维护页）

**适用对象：所有人。** 新增功能，**没有 schema 变更**。开关脚本需在**服务器上**执行。

需要临时停止对外服务时，让全站只显示一张维护页（`docs/photo/update.jpg`）。

```bash
npm run maintenance:build        # 生成维护页与 Nginx 配置（本地或服务器都行）
sudo npm run maintenance:on      # 开启维护
sudo npm run maintenance:off     # 关闭维护
npm run maintenance:status       # 查看状态（只读，不需 sudo）
```

#### 为什么走 Nginx 而不是应用层中间件

| 理由 | 说明 |
| --- | --- |
| **Node 挂了也能显示维护页** | 真在挨打时 Node 很可能已经上不来气；走应用层的方案会跟着一起挂，等于想挂维护页却挂不上 |
| **几乎不吃 CPU** | 维护页是静态文件，攻击流量在 Nginx 这一层就被挡住，落不到 Node |
| **不动现有配置** | 开/关 = 建/删一个软链，完全不碰 `sites-available/lankhub`（那份被 certbot 改过，脚本动它风险大） |

#### 行为

- 响应码 **503** —— 搜索引擎视为「暂时不可用」，**不会把站点从索引里摘掉**
- 响应头 `Retry-After: 3600` + `Cache-Control: no-store`
- **所有人都挡**（包括站长）。要在服务器上验证真实站点：`curl -I http://127.0.0.1:3000`

#### ⚠️ 维护期间证书续期

维护配置对所有请求回 503，所以**必须单独放行 `/.well-known/acme-challenge/`**，
否则维护期间证书无法续期，等恢复站点时证书可能已经过期。配置里已处理好。

#### 两个安全设计

1. **`nginx -t` 是硬门槛**：不过检查**绝不 reload**；失败时自动回滚（删软链与维护页），
   站点不受影响 —— 不会出现「想挂维护页结果把站点弄挂」
2. **维护页是 `internal`**：外部直接请求 `/__maintenance.html` 得到 404，
   只能通过 `error_page 503` 这条内部路径返回

#### 开发过程中实测踩到的两个坑（已修）

1. **`try_files $uri /index.html = 503` 返回的是 200，不是 503。**
   用真实 nginx 1.30 跑出来才发现：文件真实存在时那个 `= 503` 参数不生效，
   于是「503 + Retry-After」完全失效 —— 搜索引擎会把维护页当正常页面收录，
   而响应头里却挂着 `Retry-After`，自相矛盾。
   改用 `return 503` + `error_page 503 /__maintenance.html`。
2. **`error_page` 之后 `add_header` 不会从 server 层继承。**
   第一版只在 server 层写 `Retry-After`/`Cache-Control`，维护页虽然返回 503，
   但两个头都丢了（`add_header` 的继承是「子级自己写了就整体覆盖父级」，不合并）。
   现在两个 location 里都写一遍。

#### 顺带修掉一个部署隐患

仓库**原本没有 `.gitattributes`**，而 Windows 上 `core.autocrlf` 默认会让
`.sh` 在克隆时变成 CRLF —— **CRLF 的 shell 脚本在 Linux 上会直接报
`bad interpreter: /bin/bash^M`**，本地完全看不出来、只有部署到服务器才炸。
现在锁死 `*.sh text eol=lf`（另含 `.mjs`/`.ts`/`.conf` 等与图片 binary）。

## v0.9.5 — 2026-10-09

### 修复：PC 上歌词永远滚不到高亮行（真根因是父级的 align-items）

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**。

站长反馈：移动端正常，但 PC 又回到「一直居中的恰好是歌词中间部分、而不是高亮行」。

**这次先用 headless Edge 量了真实布局，拿到了根因**（此前三轮我都在猜，全猜偏了）：

| 布局 | main 高 | 歌词框高 | 最大可滚 | 滚到哪 |
| --- | --- | --- | --- | --- |
| `align-items: center`（旧） | 623px | **5040px**（= 内容全高） | **0** | 0（纹丝不动） |
| 去掉它 | 623px | **607px** | 2520px | 1273 ✓ 命中目标 |

**根因**：主体容器上的 `items-center`（即 `align-items: center`）会让 flex 子项
**按内容尺寸摆放**，而不是拉伸到容器高度。于是歌词框高度 = 内容全高 →
`scrollHeight === clientHeight` → **可滚动范围为 0** → 写 `scrollTop` 毫无作用。
你看到的「固定在文本中间」其实是内层 padding 撑出来的初始位置。

`min-h-0` 只解除「最小高度」限制，**管不了「不拉伸」** ——
这就是我前三轮一直没修对的原因：我盯着容器内部（padding、`min-h-0`、滚动 API），
而问题在**父级的对齐方式**上。

**为什么只有 PC 出问题**：移动端是 `flex-col`，`items-center` 作用在**横轴（宽度）**上，
纵向高度不受影响，所以那边一直正常。**这个「PC 坏 / 移动端好」的差异，
答案一直在 `flex-row` 与 `flex-col` 的区别里。**

**修法**：

- 主体改为 `items-center md:items-stretch` —— 只有移动端居中对齐，PC 拉伸填满
- 唱片那一列补 `md:justify-center` —— 去掉 `items-center` 后它需要自己纵向居中

#### 顺带修掉一个我自己引入的隐性 bug

## v0.9.4 — 2026-10-09

### 修复：PC 上滚歌词时唱片被一起滚走；歌名作者移到唱片下方

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**。

#### ⚠️ 修复：PC 上滚歌词把整个界面也滚了

站长反馈：「PC 出现严重 bug，在歌词滚动的时候**唱片也跟着滚上去了**」。
**这是我 v0.9.3 那次修复直接造成的。**

根因是 `scrollIntoView()` 的语义：它**沿祖先链逐个滚动所有可滚动的容器**，
目的是把目标带进视口。我 v0.9.3 为了让它在 PC 上「有事可做」，
把歌词内容撑到了**容器的两倍高** —— 于是整页产生了纵向溢出，
`scrollIntoView` 顺带把**页面本身**也滚了起来。页面一滚，
`relative` 定位的顶栏与主体就整体上移，看上去就是「唱片在容器里往上跑」。

**这一条同时解释了三个现象**：

| 现象 | 原因 |
| --- | --- |
| v0.9.2 之前 PC 上歌词完全不动 | 内容没溢出，`scrollIntoView` 空操作，什么也不滚 |
| 移动端一直正常 | 歌词框矮、确实溢出，它优先滚那个框，轮不到页面 |
| v0.9.3 之后 PC 上唱片跟着滚 | 溢出传到了页面层，`scrollIntoView` 把页面也滚了 |

**修法：不再用 `scrollIntoView`**（它按定义就会滚祖先，控制不了滚谁），
改成直接写歌词框的 `scrollTop`，只可能影响这一个元素：

```js
box.scrollTo({
  top: line.offsetTop - (box.clientHeight - line.offsetHeight) / 2,
  behavior: "smooth",
})
```

- 歌词框加 `relative`（`offsetTop` 相对最近的**定位祖先**，缺了会算错位置）
- **撤掉「两倍容器高」那个 hack** —— 不再需要了
- 底部歌词抽屉有同样的问题，一并改掉

#### 改进：歌名与歌手移到唱片下方（按屏幕分工）

| | 顶栏 | 唱片下方 |
| --- | --- | --- |
| **PC** | 只剩退出按钮 | **歌名（大字）+ 歌手（灰色小字）**，居中 |
| **移动端** | 保留歌名 + 歌手 | 不显示 |

移动端留在顶栏是有意的：那边是上下堆叠、空间紧，塞到唱片下面会把歌词区压得更矮。
同一份文字渲染两次、用 `md:` 断点控制显隐，视觉上永远只出现一处。

## v0.9.3 — 2026-10-09

### 修复：PC 上歌词高亮行没滚到中间；封面在唱片里显得太小

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**。

#### 修复：`scrollIntoView({block:"center"})` 在目标已可见时是空操作

站长反馈 **PC 上歌词不居中、移动端正常**，并给了一个关键线索：
「一直居中的恰好是**歌词的中间部分**，而不是高亮行」。

这条线索说明**根本没发生滚动** —— 那个「中间」是内层 padding 撑出来的初始位置，
与当前唱到哪一句无关。我第一版把根因猜成「唱片太高把歌词挤出屏幕」，是错的。

真正的原因：`scrollIntoView({ block: "center" })` **不是「把目标移到中间」**，
而是「把目标滚进视野、尽量居中」。**目标已经在可见区内时它什么都不做。**
PC 的歌词区更宽更矮，多数行本来就在可见范围内 → 一次也不滚；
移动端容器矮、确实溢出 → 一直正常。

**修法**：让内容**一定溢出**，任何一行都需要滚动才能居中：

- 沉浸层：内层 `minHeight` 取**实测容器高度的两倍**（`ResizeObserver` 跟随）
- 底部抽屉：内层加 `min-h-[28rem]`（容器是 `h-56` = 14rem）

两处都保留「上下留白 = 容器高度的一半」，否则第一行与最后一行无法居中。

#### 改进：封面在唱片里显得太小

原来封面只出现在中心圆标里，而圆标只占盘面 **37%**
（`inset-[31.5%]` 是正方形套正方形，圆形标签的真实直径还更小），
唱片一放大就显得图片很小。

现在封面出现两处：

- **盘面铺底**：`backgroundImage` 里「纹路在上、封面在下」，
  于是封面像透过黑胶看过去 —— 整张盘都有画面
- **中心圆标放大到 50%**：改用 `h-1/2 w-1/2` + 居中定位；
  无封面时的占位图标也从 26 放大到 44

#### 验证方式又改进了一步

上一轮的教训是「要验产物」；这一轮再补一条：
**断言「旧写法已移除」时不能搜整份文件** ——
我写的解释性注释里就提到了旧写法（「不用 inset-[31.5%]」、`[animation-play-state:paused]`），
第一版断言因此误报两次。现在只取 `className="..."` 属性里的内容来断言。

## v0.9.2 — 2026-10-09

### 修复：唱片暂停不停转、歌词不滚动不居中；唱片放大；歌词入口放回播放条

**适用对象：所有人。** 纯前端改动，**没有 schema 变更**，`npm run update` 可以直接跑。

#### 修复一：暂停后唱片还在转（CSS 规则顺序问题）

`animation-play-state` 原本靠额外一个 Tailwind 任意属性
`[animation-play-state:paused]` 实现，与 `.animate-disc-spin` **特异性相同（都是单类）**，
谁生效完全取决于打包顺序。实测产物里：

```css
.\[animation-play-state\:paused\]{animation-play-state:paused}   /* 先 */
.animate-disc-spin{animation:24s linear infinite disc-spin}      /* 后 → 胜出 */
```

后出现的那条 `animation` **简写**把 `animation-play-state` 覆盖掉了，所以唱片停不下来。

**修法**：把暂停收进同一个 class —— `.animate-disc-spin.is-paused`。
同一个类里声明，顺序就不可能打架。

#### 修复二：歌词完全不滚动、也不居中（容器高度自适应）

歌词容器的 class 是 `flex-1` 配 `overflow-y-auto`，但**没有 `min-h-0`**。
在 flex column 里，`flex-1` 的默认 `min-height:auto` 会让元素**被内容撑开**而不是
滚动 —— 于是容器根本没有溢出，`scrollTo` 什么也没做。

另外留白不足：即使能滚，滚到顶就是极限，**第一行与最后一行永远无法居中**。

**修法**：

- 容器加 `min-h-0`，让它真正填满可用空间并产生溢出
- 上下留白按**实测容器高度的一半**动态计算（`ResizeObserver` 跟随尺寸变化），
  这样任何一行都能滚到正中
- 改用 `scrollIntoView({ block: "center" })`，不再自己算偏移
- 切歌时也要重新居中（依赖里带上 `lyricLines`，否则「都是第 0 行」时 effect 不重跑）
- **底部那个歌词抽屉有完全相同的两个 bug，一并修掉**（`h-56` 配 `py-[7rem]`）

#### 改进：唱片放大

桌面从 `16rem / 18rem` 放大到 `26rem / 30rem`；窄屏从 `10rem / 12rem` 到 `13rem / 16rem`。
**只在桌面放到最大** —— 窄屏是上下堆叠，唱片太大会把歌词挤没。

#### 改进：歌词入口放回播放条

删除沉浸层里那行「在页面内看歌词」小字（站长反馈太隐蔽），
在播放条上加回**独立的歌词按钮**，于是两个入口都能直达：

- `ListMusic` 图标 → 底部歌词抽屉（边看歌单边看歌词）
- `ChevronUp` 图标 → 沉浸式全屏

#### 验证方式的一个改进

上一轮漏掉「暂停后唱片还在转」，根因是我**只验证了源码里写了 `[animation-play-state:paused]`，
没验证构建产物里它是否真的生效**。这一轮的断言直接读 `.next` 里的 CSS，
比对两条规则的**先后位置**，并确认旧写法已从产物里消失。

README 的 Nginx 配置新增 `limit_req_zone` / `limit_conn_zone`：
全站 10r/s（burst 20）、`/api/music/play` 2r/s（burst 5）、并发连接 20/5，
超限返回 429。README 同时给出了**验收方法**，其中包含
「正常浏览必须不被误伤」这一条 —— 误伤访客比限流失效更值得警惕。

> ⚠️ 配置里 `proxy_set_header X-Forwarded-For` **不能少**：
> 应用靠它识别客户端，一旦缺失会回退成 `127.0.0.1`，

`canAccessAdmin()` 的判据是「拥有任意一个权限码」，而 `PERMISSIONS` 现在全是内容权限。
**将来若要加非内容类权限（播放、下载…），必须先把 `canAccessAdmin` 改成只认内容权限**，

> ⚠️ **本次升级不能直接跑 `npm run update`，会中途失败。**
>
> 用户昵称（`User.name`）加上了唯一约束。Prisma 遇到「给已有数据的列加唯一索引」
> 会先给出数据丢失警告并要求 `--accept-data-loss`，而 `npm run update` 里的 `db:push`
> 没带这个参数，**会在推送数据库那一步中断**。另外如果库里已存在重名昵称，
> 加索引会直接失败，所以必须先把存量昵称整理干净。
>
> 在服务器上按顺序执行一次：
>
> ```bash
> git pull                                        # 先拿到新 schema 与整理脚本
> npm run db:normalize-usernames -- --dry-run     # 先预览会改哪些昵称
> npm run db:normalize-usernames                  # 确认后执行（幂等，可重复跑）
> npx prisma db push --accept-data-loss           # 这一次需要显式接受数据风险
> npm run update                                  # 之后照旧一键更新
> ```
>
> 整理脚本会做的事：去掉首尾空白、把编码损坏的昵称（含 U+FFFD）换成 `user-<id>`、
> 截断到 20 字、给重名依次追加 `-2`、`-3`。跑第二遍会报「无需整理」。
